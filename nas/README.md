# NAS 全自动测速钉 IP 方案（XboxDownload 的无人值守超集）

本目录是 [XboxDownload](https://github.com/skydevil88/XboxDownload) 主项目 README 第 3 节「不想开电脑下载」路线的**全自动实现**：上游方案是「路由器写 hosts 钉 IP」但需手动测速手动填；本方案在 NAS 上跑 Python 工具链，把「测速 → 选最快 IP → 写路由器 → 死亡看护 → 热备止血」整条链路无人值守化。

Xbox 主机侧**零改动**：DNS 解析被路由器 dnsmasq 钉到最快 IP，下载自动走最快线路。

## 架构

```
┌─ NAS (python3.8+, cron) ─────────────────────────────┐
│  xbox-speedtest.py  每日 04:00 全量测速               │
│    0. L0 RTT 预筛: TCP443 握手 min-of-3 → 前48        │
│    1. 8MB 粗筛(并发4) → Top8                          │
│    2. 80MB 快测排序 + 当前IP/区域保送候选             │
│    3. 冠军 vs 当前IP 稳态复测(≤8s/≤256MiB/≤文件), 换  │
│    4. uci 幂等写 dnsmasq address + restart            │
│    5. results.json 附 hotspares 热备名单              │
│  watchdog.py        每小时 :30 体检                   │
│    死/慢(<8MiB/s) → ① 热备止血(分钟级切次优)          │
│                    ② 触发 --pool 定向重测(只测坏组,   │
│                       3 小时冷却, 冷却期内只止血)     │
│  pool_refresh.py    手动: DoH(443) 解析追加新节点     │
└──────────────┬───────────────────────────────────────┘
               │ ssh (免密, ~/.ssh/id_ed25519_router)
        ┌──────▼──────┐         ┌──────────┐
        │ OpenWrt 路由 │ dnsmasq │  Xbox    │
        │ 钉 CN 域名IP │────────▶│ 自动走   │
        └─────────────┘         │ 最快线路 │
                                └──────────┘
```

## 与上游手动方案的关键差异

| 能力 | 上游 README 方案 | 本目录 |
|---|---|---|
| 选节点 | 手动测速手动填 | 三段测速自动选（粗筛→快测→稳态复测） |
| 节点死亡 | 无感知，下载变龟速才人肉发现 | 看门狗每小时体检，分钟级热备止血 |
| 防抖动 | 无 | 分组迟滞（Cn1 稳赢 15% / Cn2 稳赢 30% 才换，防夜间 CDN 波动频繁翻转） |
| 龟速节点 | 全量逐个测，可能拖数小时 | 25s 墙钟上限 + L0 预筛(全池握手取前48) + 粗筛预算，全轮约 10 分钟 |
| 幂等性 | 手写 hosts 易堆积 | uci del_list→add_list 幂等更新，重启不堆积 |

## 文件

- `xbox-speedtest.py` — 测速主程序（v2.3.36）。用法：`python3 xbox-speedtest.py [--pool Cn1]`
- `watchdog.py` — 看门狗（v2.3.36）。用法：`python3 watchdog.py`
- `pool_refresh.py` — IP 池 DNS 刷新。用法：`python3 pool_refresh.py`（目录自动取自脚本位置；写入逻辑在 `main()` 内，被 import 无副作用）
- `tests/audit.py` — **交付前机器审计**（见下节），`python3 tests/audit.py` 全绿才允许部署
- `tests/selftest_audit.py` — 审计器自检（变异测试：注入常量漂移/新失败出口/凭据泄漏/域名表缺项/阈值回归/谎报成功/假分散/稳态退化等已知缺陷，断言审计必须变红）
- `tests/replay.py` — **样本回放器**（只读，不参与决策、不写任何文件）：读 `samples.jsonl` 回答「`WIN_RATIO` 1.30 改 1.15 会多换几次、每次换来多少 MiB/s」，并逐键报字段完整率。用法：`python3 tests/replay.py [新门槛=1.15] [样本路径]`。它存在的理由是**先于**「攒够 30 天」：字段不够时攒 30 天也答不了，而那些行补不回来
- `deliver.sh` — 交付/镜像一致性（`./deliver.sh check|push|pull`；和运维台账一样只存在于部署侧，**本仓库 `nas/` 里没有这两个文件**）：把 8 个交付文件（两个主程序 + `pool_refresh` + README + `tests/` 三个 + 台账）在镜像与 NAS 之间逐项 md5 比对，`check` 有差异打印 `DIFF/MISSING-LOCAL` 并退出 1。**这 8 项是闭合白名单，只答「内容一致吗」**：新加一个交付文件只 `scp` 上去、忘了写进 `PAIRS`，表里那 8 项照样全绿 —— 所以 `check` 还列一遍 `$RD` 与 `$RD/tests` 的单侧文件（`ONLY-LOCAL` / `ONLY-NAS`，同样退 1），只忽略运行产物（`*.log` / `results.json` / `results.json.seen` / `results.json.corrupt-*` / 锁 / `IP.XboxCn*.txt`）、本脚本（NAS 无对端）和回滚点 `.bak-v2333`。**`audit.py` 只审一个目录，跨机这一层它看不见** —— 2026-11-07 就是靠人背清单同步，五个文件在 NAS 上比镜像新了没人知道。反过来，`audit.py` 现在也审这份脚本本身（`D-crlf:deliver.sh` 换行 + `D8` 的 `PAIRS` 对账），所以**两边的断言数不同是正常的**：镜像侧 168 项、NAS 侧 166 项，差的正是这两条 —— 它们用 `isfile` 守住，因为 `deliver.sh` 在 NAS 上没有对端

## 运行产物（不进仓库，`deliver.sh` 也忽略）

| 文件 | 内容 | 谁读 |
|---|---|---|
| `IP.XboxCn*.txt` | 候选 IP 池，`pool_refresh.py` 手动刷新后追加 | `rtt_rank` / `_screen` |
| `results.json` | **结论**：每组冠军 + 热备名单（`hotspares[].steady`）+ 路由器动作。读坏时先 `os.replace` 成 `results.json.corrupt-<ts>`（同名冲突再带 `-1`/`-2` 序号，**证据，别删，也永不自动清理**）再用本轮重建 —— v2.3.34 那种「读不出就不写」会让坏文件永远不被重写 | `watchdog` 判劣化 / 止血 |
| `results.json.seen` | 写成功一次就 touch 的时间戳。**唯一用途**是把 `created`（首次部署）与 `created_after_writefail`（上一轮隔离了坏表但新文件没写成，文件同样不在）分开 —— v2.3.36 之前两者同形 | 人 |
| `samples.jsonl` | **分布**：每轮每组一行 `{ts,group,l0,l0_tail,l0_pool,l0_probed,l0_alive,screen,screen_capped,screen_skip,screen_zero,screen_wave,screen_floor,screen_need,quick,quick_skip,t_l0,t_screen,t_quick,cur,wr,st_cur,st_cand,q_cur,note,ip,speed,decision}` | `tests/replay.py` 离线回放；**决策不读** |
| `speed.log` | 每轮一行摘要（`Cn1=1.2.3.4(93.6MiB/s,kept)`） | 人 |
| `run.log` / 两把锁 / `.last_retest` | cron 日志 / 串行化 / 3h 冷却标记（v2.3.34 起是 `{组: epoch}`，`--pool Cn1` 只动 Cn1 那格） | 脚本自己 |

`samples.jsonl` 是 v2.3.28 加的，立项理由写在版本历史里：`results.json` 只留结论，而 `WIN_RATIO` / `REPLACE_MIN` /
`DEGRADE_RATIO` 三个阈值全是 `n=1` 拍的。一行约 4KB（48 个 L0 握手 + 48 个粗筛分 + 48 个并发档位 + 十几条快测），
一天两轮约 12KB。**目前只 append，不 replay** —— 先攒够 30 天再写回放，否则回放的只是噪音。

路径一律**在调用时**用 `BASE` 拼（`os.path.join(BASE, ...)`），不做模块级常量：审计里每个跑 `main` 的用例都会把 `BASE` 指到临时目录，常量在 `import` 时就死了，会把夹具样本写进真文件（v2.3.29 的缺陷来源，A26 现在事后对账兜住）。A26 唯一的假红来源是**撞车**：它只认「字节有没有变」，所以 04:00 那次 cron 全量跑起来的时候跑审计（约 2 分钟），`samples.jsonl` / `speed.log` 会被真程序写 —— 红是真红，只是不赖审计。看 `speed.log` 尾行时间就能分辨，避开 03:55–04:20 这个窗口即可。

## 交付前自审（机器断言，不是人眼）

改完代码先跑，两条都过再碰 NAS：

```
python3 tests/audit.py            # 全绿才允许部署(条数以实际输出为准)
python3 tests/selftest_audit.py   # 每个变异体都必须被指定检查抓到(条数以实际输出为准)
```

需要连自己真实凭据一起查时，用环境变量传入（**不要写进仓库**）：

```
XBOX_AUDIT_DENY="我的NAS密码,我的手机号" python3 tests/audit.py
XBOX_SELFTEST=/path/to/selftest_audit.py python3 tests/audit.py   # 只在变异测试里用: 指一份改过的自检脚本, 让 A21 去读它
```

`XBOX_LEDGER` / `XBOX_SELFTEST` 两个环境变量都是给**自检**用的（台账和自检脚本都不在变异目录里，必须显式指路）；正常部署不用设。

审计分四层：

| 层 | 内容 | 拦的是哪类事故 |
|---|---|---|
| A 静态契约 | 组名/域名集合三处一致（`POOLS[4]`≡`DOMAINS`≡`pool_refresh`）、测速对一致、README 常量与代码一致、版本号一致、环境变量双向对齐、死函数、未用导入、锁文件不冲突 | v2.3.3 的「止血只切半个组」就是这一层漏的 |
| B 失败出口棘轮 | AST 统计每个函数的 `return False/None/0.0` + `except` 条数，与登记表比对；新增失败路径立即红，强制补用例 | 「修完又冒新问题」——未覆盖的失败路径变成会自鸣的数字 |
| C 行为契约 | 分类五档、采样抖动复测、整组止血、幂等、restart 失败不谎报、热备分散+下限+排序、预算截断不 KeyError、四个决策分支、`--pool` 合并落盘 | 逻辑回归（改 A 处弄坏 B 处） |
| D 交付卫生 | 凭据/私网指纹/个人路径（通用特征 + 本地私密清单）、CRLF、README 完整性、utf-8 声明 | 把密码或内网结构推到公网仓库 |

B 层登记表在 `tests/audit.py` 顶部（`FAILURE_EXITS` / `FAILURE_TESTS`）。**改了失败路径不更新它，审计会红**——这是刻意的。


## 部署

1. NAS 装 python3.8+，本目录放如 `/opt/xbox-speedtest/`
2. NAS→路由器配 ssh 免密：`ssh-keygen -t ed25519 && ssh-copy-id root@<你的路由器内网IP>`
3. IP 池文件 `IP.XboxCn1.txt` / `IP.XboxCn2.txt`（格式：`IP<TAB>(地区 运营商)`，可从上游 `IP/IP.AkamaiV2.txt` 或本地 `dig` 采集）
4. crontab（`<你的路由器IP>` 换成实际地址）：
   ```
   0  4 * * *  cd /opt/xbox-speedtest && XBOX_ROUTER_IP=<你的路由器IP> python3 xbox-speedtest.py >> run.log 2>&1
   30 * * * *  cd /opt/xbox-speedtest && XBOX_ROUTER_IP=<你的路由器IP> python3 watchdog.py >> watchdog.log 2>&1
   ```
5. 路由器侧需配套 URL 重写（302 com→cn），见主项目 [README_OpenWrt.md](https://github.com/skydevil88/XboxDownload/blob/master/README_OpenWrt.md)（lighttpd/Nginx 均可）
6. （可选，跑全量审计时需要）把项目**上一级**的 `AI共管台账.md` 一起放过去（`scp AI共管台账.md <NAS>:<项目上级>/`）。它不在项目目录里，但 `tests/audit.py` 的 A18 要读它核对条目倒序；两侧内容不一致时 A18 会红 —— 这是有意的（台账在工作区改完忘了同步，部署态就在用一份过期状态）。没放台账时 A18 **也会红**（设计上不软跳过），所以要么同步过去，要么显式 `XBOX_LEDGER=<路径>` 指一份

## 已知局限

- **`RTT_TOP=48` 是个名额，不是距离门槛**（v2.3.26）。L0 只把握手最快的 48 个交给粗筛，剩下的**一个都不测**。现在的池子（Cn1 261 / Cn2 254）里 ≤20ms 有 45 个，48 刚好不漏；但池子再长、或者运营商突然给你一批更近的边缘节点，48 就可能把「第 49 个恰好今天最快」挡在门外。它换来的是确定的执行时间：真机 261 个 × 3 次握手 5.6s，而原来按标签取子集会漏掉 21 个「标签写外省、实测 15~19ms」的近节点（长沙/南昌/福州）。**别把它当排序质量指标**：握手快只说明「近」，不代表「这台机器带宽大」—— 吞吐仍由 8MB 粗筛 + 80MB 快测 + 8s 稳态三层决定。
- **L0 测 443、测速走 80，靠的是「同一个 CDN 两个端口同源调度」这个没写进代码的假设**（v2.3.26）。`rtt_rank` 只握 TCP/443，而 `_screen` / `median_quick` / `dl_steady` 全走 80（`BindIPConn` 是 `HTTPConnection`，URL 里没有 scheme）。「443 最快的头 48 个 ≈ 80 最快的头 48 个」**没有任何一次测量验证过**，它是从「CDN 边缘节点同一套调度」推出来的。**兜底来自设计而不是数据**：L0 只发「粗筛资格」，一票决策都不投 —— 冠军是 8MB 吞吐 + 80MB 快测 + 8s 稳态测出来的。真出现「443 快、80 慢」的节点，损失是一次粗筛名额（它会在 8MB 那步被淘汰），不是一次误切换。要真验它，得给全池每个节点再加一轮 80 握手 —— 那是 261 次额外的连接，没做。
- **候选资格 = 443 可达，隐含「443 与 80 同生共死」**（v2.3.26）。三次握手全失败的直接剔除、不占名额。这条假设**有数据支持但不是断言**：本轮真机被剔的 18 个（Cn1 4 / Cn2 14）逐个复核过 80，全部同样超时 —— 所以它们是真死，不是「443 被拦」。风险面只剩「只封 443 不封 80」的节点，它会整条消失。**看日志时注意**：`RTT 预筛: 入选 48/261 个` 这个比值分不清「没测到」与「握手失败」，想知道剔了几个，得看同一轮的 `_rtt_min` 返回 None 的计数，或者直接对可疑 IP 单测 —— 别把 213 个差额当成「池子缩了」。
- **粗筛现在有总墙钟预算，代价是可能少测几个节点**（v2.3.25，`SCREEN_BUDGET_SEC=90`、`SCREEN_MIN_DONE=6`）。单节点上限从来不是常数：连接 `DL_TIMEOUT` 12s + 读数 `QUICK_MAX_SEC` 25s = 最坏 37s，4 并发 30 个节点最坏 296s，而粗筛在决策链最前面、一条决策都不产出。现在到 90s 且已完成 ≥6 个就收手，未开始的 `cancel` 掉，日志打一行「粗筛预算用尽, 余 N 个节点跳过」。**代价**：极端劣化时那 N 个没测到的节点可能是唯一还活着的 —— 所以有 `SCREEN_MIN_DONE` 保底，而且收手时行里带「余 N」，复盘看到这行要知道「这一轮的最优解可能没被测到」，别当成「全池都这么慢」
- **20MiB/s 这个门槛有三份拷贝**（`REPLACE_MIN` / `steady_top_diverse(min_steady=)` / `watchdog.HOTSPARE_MIN_MIBS`）。C44 只保证它们**现在相等**，不保证它们**是对的**——这个值正好压在 Cn2 当前 21~24 的噪声底上。再调它，先看一周 `speed.log` 里 pinned IP 的分布，别看单次样本
- **池子只保证「不再进脏的」，不保证「已经脏的清掉」**（v2.3.25）：`pool_refresh` 现在写入前校验 A 记录，只放行**公网单播 IPv4**（`0.0.0.0/8`、环回、`10/8`、`172.16/12`、`192.168/16`、CGNAT `100.64/10`、链路本地 `169.254/16`（含 `169.254.169.254` 云元数据）、组播 `224/4`、保留 `240/4` 全部拒收，日志打 `reject` + 理由）。但**已经写在池里的行不会被删**——历史脏记录仍会被 `load_ips` 收下，要清得手改池文件。为什么不用 `ipaddress` 的 `is_private` 一刀切：那个属性随 Python 版本变（3.8 里 `100.64/10` 的 `is_private` 是 `False`，3.13 才是 `True`），而 NAS 是 3.8.10、本地是 3.13 —— 用版本相关属性做安全判定，结果是「两边都绿，绿的不是同一件事」
- **没有被断言覆盖的分支，就是 bug 藏身的地方**：`st_cur == 0` 有两条子路，`cur_alive` 那条四轮没有一条断言，于是「写快测值当基准」在那躺了四个版本（v2.3.12 才被发现）。看审计覆盖率时，别只看断言条数，要看分支
- 测速文件 ≈ 游戏下载体验有误差：CDN 可能「只掐游戏内容不掐测速文件」（主机脉冲式卡顿需人工切冷节点）
- **版本化 URL 的 canary 只买「点名」，买不到「提前」**：v2.3.28 起 `watchdog.py` 每小时对 Cn2 的 URL 发一个 HEAD，非 200/206 打一行。它**不能**在微软撤版之前预警——CDN 有没有预警期（先 403 几天 / 当天直接 404）我们一次都没观测过，所以真实收益是把「`steady=0.0`，像网烂了」换成「`[canary] Cn2 HTTP 404`，是文件没了」。真止损仍然要备胎 URL，那条挂账没动。**三档文案不是修辞**：404/410 才是「文件没了」，401/403/429 是「被拒」（多半是这台出口被限流），5xx 偶发更是常态 —— 三档必须指向三个不同动作，否则运维会照着错的方向换 build。**canary 必须走明文 HTTP**（和下载路径同口径）：第一版用 `HTTPSConnection`，NAS 上真 URL 直接 `SSLCertVerificationError: Hostname mismatch`——证书不是给 `dlassets.xboxlive.cn` 签的，而下载从来不校验证书，等于每小时假警一次（A25 的第 4 条 + M87 钉住）
- Cn2 测速 URL 是写死的版本化安装包路径，**版本化 URL 是 Cn2 测量的单点**：微软下架该版本后，Cn2 的三处测量（`speedtest` 稳态、`watchdog` 每小时体检、热备止血验证）用的是同一个 URL，**没有哪一侧能免疫**。真到那天止血验证一个热备都验不出来——不是「止血慢」，是「止血做不了」，只能等全量重新入围。修法（给 Cn2 配稳定备用测速文件／自动发现版本路径）仍挂账。v2.3.17 之前这里写的是相反的话（「watchdog 已用 Cn1 文件规避」）——那是 v2.3.8 之前的实现，过期了五个版本，而且把爆炸半径说小了
- 路由器 IP 走环境变量 `XBOX_ROUTER_IP`；ssh key 路径写死在脚本头部 `SSH_KEY`（`~/.ssh/id_ed25519_router`），换环境需改这一行

- **看门狗与测速主程序必须共用 `.run.lock`**：两家都写同一个路由器。各拿一把锁时会话交错——2026-11-07 09:30 真机就是这么把 Cn2 换掉、而全量按旧快照记成 `kept` 的。看门狗拿到锁才止血，拿不到整轮跳过

- **止血记账要同时改两处，否则基准不跟着走**：`record_pin()` 只写 `grp.speed` 时，`load_record` 的优先级（先在 `hotspares` 里找 pinned IP 的旧 `steady`）会让这个实测值**到不了基准路径**——止血切到的 IP 必然来自 `hotspares`。v2.3.17 实测：写进去 100.3，下次体检基准读 105.4。现在两处一起更新（同一个原子写），C58 断言的是 `load_record` 的**返回值**，不是字段（只查字段查不出这条）
- **`.last_retest` 打在路由器可达之后**：标记早于 ssh 检查时，「路由器不通、本轮整体跳过」这种什么都没测的早退轮也占满 3 小时冷却——而路由器瞬断恰恰是最该立刻重试的时刻。C60 断言的是「早退轮没生成标记文件」（行为），不是「哪一行在前」（语法）

- **热备名单没有跨组去重**：2026-11-07 09:37 的 `results.json` 里 Cn2 的 `hotspares[1]` 是 `125.88.64.72`，那正是 Cn1 钉着的 IP。名单按运营商分散，但不按「另一组钉着的 IP」去重 → 单节点故障同时打掉两组的热备。止血前会实测所以不会切到死的，但那份「独立备胎」是假的。现只在止血时告警，改选择属阈值变更
- **台账的排序是「状态的一部分」，不是排版**：`AI共管台账.md` 头部写「新条目加在最上面」，而 2026-10-28 00:3x 之后的 25 条（含全部 11-06/11-07 记录）曾**实际追加在文件底部** —— 只读头部的人会把「最新」读成 11-05。已全部重排，并由 **A18** 钉住（条目日期单调不增 + 每条都能解析出日期 + **条数不低于 50**，跨目录靠 `XBOX_LEDGER` 指路，缺失判红不软跳过）。**教训**：任何"读文件头就知道现状"的载体，都必须有一条断言盯着它真的成立
- **A18 的条目解析不再只认顶格 `- `**：缩进两格、制表符缩进、星号、缩进星号写出来的日期条目**都参与倒序比较**（v2.3.23 前是整条跳过 —— 改个前缀再挪到底部就瞒过去了）。嵌套的无日期子项仍然放过：那不是「想写条目」，只是条目正文里的列表。条数下限 50 是「只增不改」的下界，不是目标值。
- **A18 有「层级」：只有最浅那层算条目，带日期的子项单独判红**（v2.3.24）。过去带日期的嵌套子项（正常记账：「复现于 2025-01-01」）会被当成下一个兄弟条目去比 → **假红**，而且病名报的是「逆序」，where 一点没乱；反过来砍 10 条顶层再往底部补 10 条更旧的嵌套日期子项，日期行总数守恒 → 条数下限被**灌水**绕开，仍然全绿。现在 `_rows` 带第三元「缩进深度」：排序与条数都只认最浅那层，更深的进 `_deep` 判红并给专门的 why（`日期子项=[(行号, 日期)]`）。同时日期解析从 `\d{4}-\d\d-\d\d` 放宽到 `\d{1,2}` 月/日并统一补零 —— `2026-11-1` 这种人手写完全正常的条目过去**整行隐形**（不排序、不计数、连 `_nodate` 都不进）
- **`RETEST_TIMEOUT` 到期杀子进程不会泄漏锁**：实测（NAS py3.8.10，复现 `main` 顺序）—— 子进程被 kill 后 `.run.lock` 立刻可再取，父进程退出后 `.watchdog.lock` 也可再取，父进程活着时第二实例进不来（这是对的，它在干活）。丢体检只会发生在「父进程被 5400s 上限挡住、下一小时 :30 撞上**合法持锁**」那一次，最多一次，且只在真的卡死时出现（正常 3405s 内跑完不跨 `:30`）。不要把 `[skip] 已有看门狗实例` 一律当成上一次没退出
- **`.run.lock` 建不了 ≠ 测速在跑**：`run_lock_taken()` 有三种结果（fd / False / `LOCK_ERR`），把 I/O 失败混进 False 会让止血永久跳过、日志每小时指着一个不存在的并发进程。看到 `[skip] 无法创建 .run.lock`要去查目录权限/磁盘，不是查进程
- **每组要切的域名有两个来源**：speedtest 的 `POOLS[i][4]`（钉哪些）与 watchdog 的 `DOMAINS`（止血时一起切哪些）。两处必须一致，否则止血只切一半域名、主机仍命中死 IP（v2.3.3 修复项）；改动任一处请同步另一处
- 热备分散只能「尽量」：若当下只有一家运营商的节点可达（实测 2026-11-06 晚间广东电信段整体掉到 1MiB/s），名单仍会集中在同一家 —— 这是网络实况，不是代码问题
- **稳态测速是「时间 × 字节 × 文件大小」三限**：`8s`、`256MiB`、以及测速文件本身的大小同时生效。NAS 真机 HEAD 实测：Cn1 的 `extraextralarge.txt` = 309714493B（**295.4MiB**），100MiB/s 下最多跑 3.0s；Cn2 的版本化包 40.4GiB（时间/字节先到）。所以「8s 稳态」实际窗口只有 **2.6~2.9s**，这是物理上限，不是 bug。再往上调字节上限会让单轮流量进入十几 GB 量级
- **单轮全量测速的流量账**：`STEADY_MAX_BYTES=256MiB` × `STEADY_ROUNDS=3` 次 × **实际上开机测的节点数**。别按「候选数」估：候选 4 个不等于测 4 个 —— 冠军 / 当前 IP 还各有一次独立的 `median_steady`。2026-11-07 00:44 那轮（v2.3.8）实测 **每组 4.02GiB、合计 8.04GiB**，而按候选数算只有 3GiB/组，差额就是这些独立调用再加上「冠军被测两次」的老 bug（v2.3.9 已修：修后同一场景复跑 **7.49GiB / 10 个节点**，10×3×256MiB=7.50GiB 正好乘平；单组约 3.75GiB）。脚本自己记的稳态账（日志末尾 `[t] 稳态复测累计传输 … 实测节点 N 个`）是唯一可归因的数。**别拿 `/proc/net/dev` 当账本**：同一轮 enp3s0 接收增量 **13.2GiB**、kvmbr0 **12.8GiB**，差出来的 6GiB 是 NAS 上其他容器/虚拟机的流量，脚本无关；粗筛+快测本身约 0.9GiB。所以网卡计数器只能当上界，2026-11-06 记的「9.58GiB」同样是上界，不是本脚本的流量
- **两个测速函数的计量口径必须一致**：`dl_steady` 与 `watchdog.steady` 都从**首个响应头到达**开始计时（TCP 握手/首字节延迟不算吞吐）。交替测 4 轮实测均值差 0.8%，而单个节点的抖动本身有 22% —— 想验证「改口径有没有用」，必须交替多轮取均值，单次对比得出的百分比不可信
- **看门狗哨兵口径与 speedtest 对齐**：`STEADY_MAX_BYTES=256MiB`（两处常量必须一致），每小时两组约 **0.5GiB**。**Range 跨度不得等于字节上限**：真机实测 `dlassets`（Cn2）对 `span=256MB` / `512MB` 一律 12s 超时（两个备用 IP 都一样），`8/64/80/160MB` 才正常返 206 —— 跨度超过 CDN 容忍值会让 `dl_steady` 全部返回 0，而 0 又被下游读成「节点已死」，一次就能把 93MiB/s 的节点换成 14MiB/s 的（2026-11-07 真实发生）。现取 `RANGE_SPAN=160MiB`，安全窗 8~160MiB，audit 的 C30b 钉这个窗
- **测速窗口会被「单连接 ~190MiB 塌陷」截断**（2026-11-07 真机逐秒打点）：Cn2 的 40.4GiB 包，前 1s 跑 89MiB、5s 到 191MiB，然后**停住**，8s 窗口只收到 192MiB ⇒ **21~24MiB/s**；同一时刻换 Cn1 的小文件（295MiB）测也是在 196MiB 处塌陷。首段突发 90~105MiB/s 是真的，塌陷也是真的 —— **「测速 100」与「实下 40」不矛盾**：8s 窗口的平均本来就只有 20~25；同理**不同窗口的测量值不能相减**（2s 突发 vs 8s 平均）
- **两组用的测速文件完全不同，数值不可横向比较**：Cn1 是 295.4MiB 的静态小文件，Cn2 是 40.4GiB 的版本化安装包，真机同一时刻能差 5 倍（拿 Cn1 的文件测 Cn2 的 IP 得 98~105，用它自己的包得 21~24）。`watchdog.steady()` 的 `host/path` 因此**取消默认值**：v2.3.8 之前它默认指向 Cn1 的文件，而 main 里两处 `steady(ip)` 没传参 —— Cn2 的每小时体检一直在测 Cn1 的文件、再拿去比 Cn2 大包的记录，`degraded` 永不触发
- **Cn2 的稳态测量抖动可达 4 倍**（同一 IP 一晚：14.1 / 21.3 / 23.9 / 82.6 / 93.8 / 95.x），远大于 `WIN_RATIO` 的 1.3 倍迟滞。日志里出现 `[t] 稳态离散 ...` 就说明这一轮判定受抖动影响，别把它当硬数据复盘。真要压住它，要么加轮次取上分位、要么拉长窗口，两者都加流量，尚未做
- **`REPLACE_MIN=20MiB` 正压在 Cn2 的平台期（21~24）上**：这是目前唯一有数据支撑的下限，也是最脆的一个数 —— 全网都在 20 上下时，它既可能挡住本该做的替换、也可能放行一个噪声内的候选。真正的死/活判据是 `cur_alive`（快测 8MB 小块），`REPLACE_MIN` 只是第二道闸。**再调这个数先看一周 speed.log 的分布，别看单次样本**
- **auto 标签节点没有运营商信息**：`pool_refresh` 生成的 `(autoMMDD 域名)` 标签里没有运营商，热备分散把这类节点按「未知 ≈ 同一家」处理，第一轮只占一个位（不再把别家运营商挤掉）—— 宁可名单短，也不假装分散
